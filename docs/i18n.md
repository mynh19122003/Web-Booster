# Frontend localization

UI copy is split by interface area under `lib/i18n/catalog/`: `layout`, `home`, `services`, `auth`, `dialogs`, `regions`, `rank`, `support`, `pages`, and `common`. Add a stable key to the relevant area file in all four base locale objects (`en`, `vi`, `zh`, `ko`). The 20 additional locale catalogs are split by area under `lib/i18n/catalog/locales/<locale>/`. `MessageKey` is assembled in `lib/i18n.ts`, so `t("key")` is type checked. Use placeholders such as `{count}` and pass values through `t("key", { count })`; avoid joining translated fragments into a sentence when word order can differ.

Client components read the saved language with `useLanguage()` from `components/ui/LanguageProvider.tsx`. The header writes the selection to `localStorage` only after Save, then reloads the page. Add language metadata and its `Intl` locale to `languages` and `intlLocales`, and add a localized flag to `components/ui/LanguageFlag.tsx`. `useMoney()` uses the active locale for number formatting; currency remains a separate selection.

The language menu offers 24 locales. The four base languages have area-based catalogs under `catalog/`; the 20 additional locales have 372 catalog keys each, split into area files. Static page introductions, service descriptions, FAQs, and mock reviews use separate per-locale files under `data/locales/` (66 strings per locale). Run `node scripts/generate-locale-catalogs.mjs --check` to verify message-key and placeholder coverage, `node scripts/generate-locale-catalogs.mjs --check-content` to detect exact English content fallbacks, and `node scripts/verify-locales.mjs` to check representative home and game page text in the running local site.

Longer content has its own keyed data: static page introductions in `data/page-copy.ts`, service names and descriptions in `data/service-copy.ts`, FAQ entries in `data/faqs.ts`, and mock reviews in `data/reviews.ts`. Add locale variants there instead of putting page copy in JSX. Proper names, game ranks, user input, and remote API messages are content rather than UI labels.

The additional locale strings were generated as machine-translation drafts and need native-language review before release, especially service terms. Legal policy bodies and the internal admin workspace are outside the customer-facing localization catalogs and remain in English. Remote review text stays in the language it was submitted in; bundled mock reviews have localized variants. Language preference is stored in browser local storage, so it does not select server-rendered metadata or provide locale-specific URLs.
